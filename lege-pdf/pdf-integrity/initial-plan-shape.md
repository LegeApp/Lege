# Verdict

This is **relatively achievable from the current Lege codebase**, provided the product is framed correctly:

> A local PDF integrity and forensic-triage utility that reports recoverable revision history, structural modifications, overlays, rasterization, signature coverage, and document inconsistencies.

It should **not** claim to determine whether a person committed fraud. Fraud involves intent and external facts. A PDF can reveal that content changed, how it changed, and sometimes exactly what the previous content was. It usually cannot establish why it changed.

The useful stopping point is:

1. Recover and classify logical PDF revisions.
2. Identify explicit annotations and overlays over existing text.
3. Identify changes to page content, fonts, images, and page structure between revisions.
4. Classify pages as vector, raster-only, raster-plus-OCR, or mixed.
5. Inspect digital-signature coverage and post-signature changes.
6. Produce an explainable JSON and human-readable report.

That is a moderate extension of what you already have, not a second renderer project. Detecting a carefully rewritten or print-scanned forgery from a single standalone PDF is a different and much larger image-forensics problem.

# PDF-Verse is an especially easy case

The linked PDF-Verse editor does **not** save its edits as annotations over the original PDF.

Its editor:

* renders every original PDF page through PDF.js into a canvas;
* uses that rendered canvas as the Fabric.js background;
* adds text, drawings, images, and shapes to the canvas;
* creates a new jsPDF document;
* embeds each complete canvas as a full-page PNG or JPEG.

The original PDF objects, fonts, text streams, annotations, and revision history are discarded.

Your tool would identify its output approximately as:

```text
document representation: full-page raster
pages with visible PDF text: 0 / 12
pages with embedded fonts: 0 / 12
pages dominated by one full-page image: 12 / 12
recoverable prior revisions: 0
editable source structure preserved: no
```

That proves that the submitted file is a flattened raster export. It does **not** prove that its contents are fraudulent, because a scanner, print-to-PDF workflow, legitimate privacy flattening, or an ordinary image-to-PDF converter can produce the same broad structure.

The more useful finding is often an inconsistency:

```text
pages 1–5: vector text generated by Microsoft Word
page 6: one full-page JPEG, no text or fonts
pages 7–9: vector text generated by Microsoft Word
```

That is substantially more interesting than a 200-page book in which all 200 pages are normal scanned images.

# The first necessary parser correction

Do not reinterpret the current `snapshot.structure().revisions.len()` as “number of times the document was edited.”

At present:

```rust
pub struct Revision {
    pub xref_offset: u64,
    pub trailer: Arc<Dictionary>,
}
```

The loader processes sections newest to oldest with first-write-wins semantics. For classic xrefs, it temporarily collects the section’s entries and then discards them after merging. For xref streams, it immediately merges the entries. Consequently, you know that sections existed, but not which objects each section introduced.

There are also two important counting problems:

1. A hybrid-reference revision has a classic xref table plus an auxiliary `/XRefStm`. The current loader pushes a `Revision` for the classic table and another for the xref stream. Those are two xref sections, but usually one logical save.
2. Linearized PDFs can contain initial stub structures and additional xref sections that are not evidence of a later human edit.

Model these separately:

```rust
pub enum XrefSectionKind {
    Classic,
    Stream,
}

pub struct XrefSection {
    pub offset: u64,
    pub kind: XrefSectionKind,
    pub entries: Arc<[RevisionXrefEntry]>,
    pub trailer: Arc<Dictionary>,
    pub prev: Option<u64>,
    pub auxiliary_of: Option<u32>, // /XRefStm relationship
    pub recovery: Arc<[RecoveryEvent]>,
}

pub struct LogicalRevision {
    pub chronological_index: u32,
    pub primary_section: u32,
    pub auxiliary_sections: Arc<[u32]>,
    pub start_offset: u64,
    pub end_offset: u64,
    pub boundary_confidence: BoundaryConfidence,
}
```

PDF incremental updates append changes, and an update’s xref section can contain only objects that were added, modified, or deleted. `/Prev` links it to the preceding xref section. That is exactly the information your loader already follows; it simply needs to preserve it rather than immediately collapsing it. ([Errata for PDF specifications][1])

For each logical revision, derive:

```rust
pub enum ObjectChange {
    Added,
    Redefined,
    Freed,
    RepeatedIdentically,
}
```

Then classify affected objects:

```text
page
page tree
page contents
font
font program
ToUnicode
image XObject
form XObject
annotation
annotation appearance
AcroForm field
signature
metadata
other
```

This is the core of the utility.

# Detection feasibility by editing method

| Editing method                                                                |                        Detectability from one PDF | Assessment                                                                        |
| ----------------------------------------------------------------------------- | ------------------------------------------------: | --------------------------------------------------------------------------------- |
| Explicit `FreeText`, `Stamp`, `Square`, `Redact`, image or similar annotation |                                         Very high | Existing annotation parser and rendering path cover most of it                    |
| Annotation appearance covering existing text                                  |                                         Very high | Compile with and without annotations; intersect changed pixels with glyph boxes   |
| White rectangle and replacement text appended to page content                 | High when saved incrementally; moderate otherwise | Revision diff finds changed content; painter-order analysis finds occlusion       |
| Existing content stream directly edited using the same embedded font          |                High when revision history remains | The content object is redefined even though the font is unchanged                 |
| Page `/Contents` replaced with a new stream                                   |                        Very high when incremental | Direct object and semantic text change                                            |
| PDF fully rewritten after a vector-text edit                                  |                                   Low to moderate | Old history is gone; only consistency heuristics remain                           |
| Whole document rasterized                                                     |                Very high as a representation fact | Cannot distinguish malicious rasterization from legitimate scanning by itself     |
| One page rasterized among otherwise vector pages                              |                                High as an anomaly | Strong review indicator, but still not proof                                      |
| Small raster patch placed over vector text                                    |                                  Moderate to high | Image geometry and painter order can identify it                                  |
| Document printed, edited physically and rescanned                             |                                               Low | Becomes an image-forensics problem                                                |
| Forged document generated coherently from scratch                             |                             Generally unavailable | Nothing in the PDF necessarily distinguishes it from an honest generated document |
| Content changed after a digital signature                                     |                            Potentially conclusive | Depends on signature validity and permitted modification policy                   |

The right product claim is therefore **“detect and explain recoverable tampering indicators”**, not “detect every forged PDF.”

PDF forensic practitioners make the same distinction: incremental saves can preserve highly useful change history, but legitimate actions such as form filling, optimization, signatures and notary stamps also alter PDFs, making intent difficult to infer. ([PDF Association][2])

# Scenario 1: annotation overlays

This is your quickest high-value feature.

PDF annotation appearance streams are painted on top of page content. ([Errata for PDF specifications][3]) Your renderer already supports:

```rust
AnnotationMode::None
AnnotationMode::StaticAppearances
```

and the compiler tags annotation appearance operations as:

```rust
PaintOrigin::AnnotationAppearance
```

## Detection procedure

For every page containing relevant annotations:

1. Compile and render the page without annotations.
2. Compile and render it with annotations.
3. Compute the changed-pixel mask.
4. Build the page’s text geometry without annotations.
5. Intersect changed pixels with character and word boxes.
6. Resolve the annotation subtype, object, rectangle and appearance stream.
7. Report the underlying text affected by the annotation.
8. Optionally extract replacement text from the appearance stream.

An evidence record could say:

```text
Finding: explicit annotation affects existing text
Page: 1
Annotation object: 44 0
Subtype: FreeText
Rectangle: [318.2, 442.8, 394.1, 461.3]
Affected underlying text: "2.84"
Annotation appearance text: "3.84"
Glyph-area coverage: 96%
Revision introduced: 2
```

That is much better than merely reporting “one FreeText annotation.”

## Required annotation-model additions

`PageAnnotation` currently preserves the rendering fields but not the annotation object identity or forensic metadata. Add:

```rust
pub struct PageAnnotation {
    pub object: Option<ObjectId>,
    // existing fields...

    pub contents: Option<PdfString>,
    pub unique_name: Option<PdfString>,   // /NM
    pub modified: Option<PdfString>,      // /M
    pub created: Option<PdfString>,       // /CreationDate
    pub author: Option<PdfString>,        // /T
    pub subject: Option<PdfString>,       // /Subj
    pub intent: Option<NameId>,           // /IT
}
```

Do not treat all annotations as suspicious:

* highlights and comments are normal;
* widgets can be legitimate form fields;
* signatures have widget appearances;
* redaction annotations may be preparatory rather than applied;
* stamps may be approval or notary marks.

The meaningful question is whether an annotation creates opaque or replacement-looking content over existing text, when it appeared, and whether it was allowed by a signature policy.

# Scenario 2: overlays flattened into page content

Not every editor uses annotation objects. For example, the PDF Association reported in January 2026 that Chrome’s drawing feature writes ink into page content streams rather than normal PDF annotations. ([PDF Association][4])

A crude editor may append something like:

```text
save graphics state
draw opaque white rectangle
draw replacement text
restore graphics state
```

or place a Form XObject or image over the original text.

## Detection procedure

Use painter order to find:

1. A visible text run.
2. A later opaque path, Form XObject or image overlapping that text.
3. Optionally, another text run placed over the covered area.

The existing display list already has the relevant ordering, paints, alpha values, text runs and images. The missing piece is exact source provenance.

Your current attribution map records:

```text
leaf: text / image / path / shading
origin: page content / form / annotation / pattern / Type 3
```

But it intentionally ignores alpha, blend modes and soft masks, and only records a broad containing category. Therefore it is a good candidate generator, not final forensic evidence.

Add an **optional compile trace sidecar**:

```rust
pub struct PageTrace {
    /// Parallel to SemanticPage::ops.
    pub op_sources: Arc<[SourceRef]>,
}

pub struct SourceRef {
    pub stream_object: Option<ObjectId>,
    pub nested_object_stack: Arc<[ObjectId]>,
    pub byte_span: Option<Range<u64>>,
    pub operator_index: u32,
    pub origin: PaintOrigin,
}
```

Do not widen every normal renderer operation with forensic data. Produce this only in audit mode.

The overlay analyzer can first perform cheap geometry checks, then rasterize only candidate regions at higher resolution to determine actual coverage. That avoids allocating a full object-ID plane for every page.

# Scenario 3: direct text edits using the embedded font

Using the same font does not materially defeat revision-based detection.

Suppose an editor changes:

```text
(2.84) Tj
```

to:

```text
(3.84) Tj
```

using the existing `/F3` font.

If the file was incrementally saved, at least one of these usually occurs:

* the content-stream object is redefined;
* a new content stream is added and the page `/Contents` reference changes;
* the page dictionary is redefined;
* a new Form XObject is added and invoked;
* a page resource dictionary is changed.

The xref update identifies the changed object regardless of whether the font changed. Replaying the earlier revision gives the exact old text and appearance.

## Revision replay

Add a bounded source to `pdf-source`:

```rust
pub struct PrefixSource {
    inner: Arc<dyn PdfSource>,
    end: u64,
}
```

For every reliable logical revision boundary:

```text
original bytes[0..revision.end_offset]
    ↓
DocumentSnapshot::open
    ↓
compile text and render pages
```

This lets you use the existing parser, text extractor and renderer without creating a special historical-document implementation.

Then compare consecutive revisions at three levels:

1. **Object diff:** which objects were added, redefined or freed?
2. **Semantic diff:** which words, glyphs, fonts, images or page relationships changed?
3. **Visual diff:** which pixels and page regions changed?

A report can then say:

```text
Revision 2 redefined object 17 0, used as page 1 /Contents.
Text changed:
    previous: "Cumulative GPA: 2.84"
    current:  "Cumulative GPA: 3.84"

Visual difference:
    page 1, rectangle [291.5, 441.6, 397.8, 463.4]
```

That is a strong and explainable result. It establishes modification, though not fraudulent intent.

## The hard boundary

If the editor performs a complete rewrite or “Save As,” the earlier object definitions may be gone. A perfectly coherent rewritten PDF using the original embedded font can be structurally indistinguishable from a PDF generated honestly with that text from the beginning.

At that point you only have heuristics:

* one text line uses a different font object or font-program hash;
* text spacing and `TJ` style differ from surrounding lines;
* a new font subset has unusual glyph coverage;
* one stream has a different filter or serialization style;
* object numbering or resource naming changes abruptly;
* producer and modification metadata disagree;
* a local image patch appears over otherwise vector content.

These can prioritize human review. They should not be presented as strong evidence.

Your existing `SemFont` and `TextRun` already preserve embedded font bytes, font object identity, size, text matrix, spacing, horizontal scaling and raw `Tj`/`TJ` elements. Therefore basic font-consistency analysis does **not** require OCR.

# Scenario 4: rasterization

You can identify raster representation without OCR.

For each page, calculate:

* visible text-run count;
* hidden or extraction-only text-run count;
* font count;
* image count;
* image coverage of the crop box;
* vector path coverage;
* image pixel dimensions;
* effective horizontal and vertical DPI;
* codec, color space and bits per component;
* whether the image is a single full-page image;
* whether an invisible OCR text layer exists.

Use factual classifications:

```rust
pub enum PageRepresentation {
    Vector,
    RasterOnly,
    RasterWithTextLayer,
    Mixed,
    Blank,
    Unknown,
}
```

Avoid a class called `FraudulentlyRasterized`.

## Document-level consistency matters more than rasterization itself

Useful findings include:

```text
FULL_PAGE_RASTER
All 18 pages consist of full-page images.
No prior vector structure is recoverable.
```

and:

```text
REPRESENTATION_OUTLIER
Page 4 is raster-only.
The other 11 pages contain vector text and share three embedded fonts.
```

and:

```text
LOCAL_RASTER_PATCH
Page 2 contains a 612×84 JPEG placed over a text-heavy vector page.
The image occupies one row of a table.
It first appears in revision 3.
```

PDF-Verse output would normally trigger the first case.

OCR becomes useful later for:

* comparing a page image against an invisible OCR text layer;
* detecting hidden-text versus visible-text disagreement;
* reading a raster patch and comparing it with previous text;
* identifying possible typeface or baseline anomalies in a raster-only document.

It does not need to be in the initial utility.

Raster-image forgery localization should remain a separate research module. A 2026 cross-dataset benchmark found that current document forgery detectors could have moderate ranking performance while producing very poor fixed-threshold localization because their scores were badly calibrated across document domains. ([arXiv][5])

# Digital signatures should be treated separately

Digital signatures are the strongest available single-file integrity evidence, but signature validation has several distinct layers:

```text
1. Is the signature dictionary structurally valid?
2. Is /ByteRange valid and associated with a real revision boundary?
3. Does the cryptographic digest validate?
4. Is the signer certificate trusted?
5. Was it valid at signing time?
6. Were later changes permitted by DocMDP or FieldMDP?
```

The PDF specification expects the signature byte range to cover the document through the `%%EOF` terminating the revision that introduced the signature, excluding only the signature value itself. ([Errata for PDF specifications][6]) DocMDP and FieldMDP can restrict which later document or form-field changes are allowed. ([Errata for PDF specifications][6])

Implement this in layers:

### Initial signature support

* find AcroForm fields with `/FT /Sig`;
* parse signature dictionaries;
* validate `/ByteRange` shape, ordering and file bounds;
* associate each signature with a logical revision;
* identify bytes and logical revisions appended afterward;
* parse DocMDP and FieldMDP policies;
* report structural status without claiming cryptographic validity.

### Later cryptographic support

* verify CMS/CAdES digest;
* parse certificates;
* check certificate chain and trust;
* optionally handle timestamp and revocation material;
* determine whether later modifications comply with certification policy.

Do not write a homegrown PKI validator merely to complete the first version. Structural signature coverage alone is already useful. Full trust validation should use a mature cryptographic implementation.

Also, signature validation must use the original bytes and a stricter parse policy. Tolerant PDF processing has historically contributed to signature-validation vulnerabilities, especially where malformed xrefs and incremental updates are interpreted inconsistently. ([PDF Association][7])

# Strict versus tolerant parsing

The renderer correctly prioritizes opening and displaying malformed real-world documents. Forensics has a different requirement: repairs must not silently become facts.

Use two outcomes:

```rust
pub struct ParseAssessment {
    pub strict: StrictOpenOutcome,
    pub tolerant: OpenOutcome,
    pub repairs: Vec<RecoveryEvent>,
}
```

The initial implementation does not need an entirely separate strict parser. It can:

1. Hash and inventory the raw bytes.
2. Record every structural anomaly before interpretation.
3. Open through the existing tolerant path.
4. Mark evidence derived from a recovered xref as such.
5. Refuse to make cryptographic or historical claims when reconstruction is ambiguous.

Eventually add:

```rust
pub enum RecoveryPolicy {
    AllowAndRecord,
    Forbid,
}
```

A file requiring xref reconstruction is not necessarily fraudulent. It may merely have been damaged by a transfer, producer bug or bad optimizer.

# Report model

Avoid a single opaque “fraud score.” A score such as `87% fraudulent` would be scientifically weak and potentially harmful in admissions or employment workflows.

Use categorical evidence:

```rust

    CryptographicFact,
    StrongDerived,
    ContextualIndicator,
    WeakHeuristic,

pub struct Finding {
    pub code: FindingCode,

    pub summary: String,

pub struct AuditReport {

Extend `pdf-read` and add the report schema.

Implement:

* xref-section inventory;

Acceptance fixtures:

PDF-Verse output

malformed but recoverable PDF
linearized PDF

```

## Milestone 2 — correct logical revision history

Refactor the structure layer to preserve `XrefSection` entries.

Implement:

* classic and stream section entries;
* hybrid grouping;
* valid `startxref` and `%%EOF` boundaries;
* oldest-to-newest logical revision order;
* linearization/stub distinction;
* `Added`, `Redefined`, `Freed`, `RepeatedIdentically`;
* raw and semantic object hashes;
* object-role classification;
* reverse mapping from objects to affected pages;
* `PrefixSource`;
* extraction or opening of historical revision snapshots.

Be careful not to find `%%EOF` merely with a raw byte substring search; that sequence can occur in stream data. Pair a syntactically valid `startxref` value with its following EOF marker.

When the xref has been rebuilt by scanning, report that original revision membership cannot be established reliably.

## Milestone 3 — revision comparison and overlay evidence

Implement:

* text diff between revisions;
* deterministic render diff between revisions;
* connected changed-region extraction;
* annotation-on versus annotation-off render diff;
* underlying-text extraction;
* annotation appearance text extraction;
* candidate page-content occlusion detection;
* optional `PageTrace` provenance sidecar;
* evidence PNGs or SVG overlays.

For deterministic evidence, use the CPU renderer and disable system-font substitution by default. GPU rendering can remain an optional fast preview.

This milestone delivers the genuinely useful product.

## Milestone 4 — signature verification

Implement:

* strict ByteRange validation;
* digest verification;
* CMS/CAdES parsing;
* certificate chain and trust reporting;
* timestamp status;
* DocMDP and FieldMDP compliance;
* exact post-signature object changes.

Keep these statuses separate:

```text
digest valid
certificate trusted
certificate time-valid
later revision present
later change permitted
```

A cryptographically valid signature does not prove that the signed claims were truthful; it establishes integrity since signing and identifies a credential, subject to trust validation.

## Milestone 5 — optional consistency heuristics

Only after testing the first four milestones:

* embedded font-program hashes;
* text-run spacing and matrix outliers;
* neighboring-line font inconsistency;
* stream-filter and serialization outliers;
* resource-name and object-number clusters;
* metadata timeline inconsistencies;
* image DPI, codec, quantization and color outliers;
* producer fingerprints.

These should remain weak or contextual indicators until validated against a broad legitimate corpus.

# Testing strategy

Your existing `pdf-test-support` is a significant advantage. Extend it to generate controlled files for:

* annotation added in a later revision;
* annotation with an appearance covering text;
* white rectangle and replacement text in a new content stream;
* existing content stream redefined while reusing the original font;
* page `/Contents` changed from one object to an array;
* image patch placed over text;
* full-page raster replacement;
* OCR text layer behind an image;
* metadata-only update;
* signature-only update;
* permitted form fill;
* post-signature page-content edit;
* classic xref, xref stream, hybrid xref and object-stream variants;
* linearized and malformed versions.

Also collect legitimate outputs from:

* Acrobat;
* browser print-to-PDF;
* Chrome drawing;
* macOS Preview;
* Microsoft Office;
* LibreOffice;
* scanner software;
* OCR software;
* PDF optimizers;
* signing and form-filling programs;
* PDF-Verse;
* pdf-lib and jsPDF.

Label the operation that produced each fixture, not whether it is “fraudulent.”

Use qpdf’s object and JSON output as a differential test oracle for xref and object inventory, while keeping the released application fully Rust-native. ([QPDF][8])

A directly related beta utility, `revpdf`, was released in April 2026 and already reports revision byte ranges, object-level changes, and annotation-only versus content-affecting updates. That validates the basic product surface. Your differentiator would be the integrated semantic text extractor, renderer, visual attribution and high-performance revision comparison. ([PyPI][9])

# What not to build initially

Do not begin with:

* OCR-based font matching;
* a neural “fraud probability” model;
* JPEG error-level analysis;
* noise-residual or copy-move detection;
* automated deletion or rollback of “suspicious” objects;
* a GUI;
* automatic admissions or employment rejection;
* exhaustive PKI validation;
* producer-specific fingerprints as primary evidence.

Also keep the first version read-only. Automatic cleanup complicates evidence preservation and increases the risk of removing legitimate content.

# Final recommendation

Proceed with the project, but call it something like **Lege PDF Audit**, **Lege Integrity**, or `lege-pdf-audit`, not a definitive fraud detector.

The first useful release should cover:

```text
raw file hash
+ neutral structural report
+ correct logical revision history
+ object-change classification
+ explicit annotation/text overlap
+ revision text and visual diffs
+ raster/vector page classification
+ structural signature coverage
+ JSON and evidence output
```

That scope is well matched to your current parser and renderer. The main work is preserving per-section xref information and revision boundaries, then connecting existing text and rendering machinery into an evidence report.

Stop after revision diff and overlay evidence, evaluate it on legitimate and controlled-edited documents, and only continue into font heuristics or raster image forensics if the explainable structural utility is already producing useful results.
